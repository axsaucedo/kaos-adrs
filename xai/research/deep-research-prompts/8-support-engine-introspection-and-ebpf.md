You are doing deep research to verify the engineering feasibility of a specific open-source design, not a general literature review. Read the context, then do the task. Precision about what is a documented, supported extension point vs a fork/patch vs impossible is the whole point.

CONTEXT — the project. `xai` (github.com/EthicalML/xai) is an open-source library from The Institute for Ethical AI & ML, first released in 2017 for tabular ML explainability/fairness, being revitalized in 2026 for agentic LLM systems. One optional layer (F) instruments a self-hosted open-weights INFERENCE SERVER to emit model-internal signals — per generation step: logit-derived uncertainty (entropy, logprob margin), one or more linear-probe readings on the residual stream, and optionally attention/attribution — as OpenTelemetry spans correlated to the agent's trace via W3C `traceparent`. The design distinguishes a cheap "monitor mode" (logit stats + linear-probe scalars, meant to run inline in a throughput server) from a heavy "deep mode" (full activation capture, only viable on single-request dev boxes). The intended integration is a LOAD-TIME PLUGIN that registers forward hooks, NOT a fork of the engine. Firm non-goals: no sparse-autoencoder trainer, no circuit-discovery framework; store probe scores and top-k attributions only, never raw activations.

CONTEXT — the claims to verify. The design currently assumes: (1) for PyTorch-based engines (vLLM, SGLang) a `torch.nn.Module.register_forward_hook` can be attached from a load-time plugin without forking, and a linear probe is one cheap matmul on the residual stream; (2) vLLM's continuous batching / paged attention makes mapping an activation back to a specific request the hard part; (3) TensorRT-LLM is compiled and exposes no runtime module graph, so activations need an engine rebuild with debug tensors as outputs — logit-only otherwise; (4) llama.cpp / Ollama (C++/GGML) has no PyTorch hooks but tensors live in host RAM, reachable via ggml callbacks; (5) eBPF (including bpftime's GPU-side PTX injection) and CUPTI can observe execution/timing/memory (a "cost channel") but cannot recover semantically-labeled activations, because tensor identity is a model-graph concept absent at the kernel/PTX layer.

TASK. Verify or correct each of the five claims above against current (2025–2026) documentation, source code, issues/PRs, and credible write-ups. For each inference engine — vLLM, SGLang, TensorRT-LLM, llama.cpp/Ollama, and (briefly) MLX and NVIDIA Triton as a backend-agnostic server — determine concretely:
- What is the officially supported extension/plugin/hook mechanism, if any, and whether custom per-step activation reads can be added WITHOUT forking (cite the specific API, plugin system, or the absence of one).
- The realistic cost and memory impact of a single linear-probe read inline at serving throughput.
- How the engine's batching/scheduling complicates attributing a read to a specific request, and whether any existing feature (request IDs, per-sequence hooks, logprobs API) helps.
- The current state of activation-capture forks, PRs, or third-party plugins for that engine.
For eBPF/CUPTI: confirm the boundary between what they CAN provide (kernel timing, memory, launch counts, per-request GPU cost) and what they cannot (labeled residual-stream tensors), including the current capabilities and limits of bpftime's GPU-side instrumentation. Also check for any existing project that already emits model-internal signals from an inference server as OpenTelemetry spans.

OUTPUT. Structured markdown with inline citations to primary sources (docs, source files, issues/PRs, papers) at each claim. For every engine give an explicit verdict: "supported plugin", "requires fork/patch", or "not feasible", for both monitor-mode (probe scalar / logit stats) and deep-mode (full activations) separately. State clearly which of the five design assumptions are confirmed, which need revision, and what the safest first-target engine is for a load-time-plugin monitor-mode implementation. End with the specific risks that only a runnable spike (S3 on vLLM/SGLang, S4 on llama.cpp, S5 on eBPF) can retire.
