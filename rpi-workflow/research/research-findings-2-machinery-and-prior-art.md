# Research findings 2 — Plugin machinery and prior art

Distilled findings for [Area 2](proposed-research.md) of the RPI workflow plugin research, against the baseline in [000-initial-request](../adrs/000-initial-request.md). Full captured material: [ref 2-1 HumanLayer RPI](research-ref-2-1-humanlayer-rpi.md), [ref 2-2 plugin machinery](research-ref-2-2-plugin-machinery.md), [ref 2-3 prior-art flows](research-ref-2-3-prior-art-flows.md).

Research window: ~30 minutes, August 2026. Sources are current as of that date; the ecosystem moves fast enough that the CRISPY/plan-mode details below should be re-checked before the ADR stage closes.

## A. The original RPI — what it actually prescribes

**1. The creators are HumanLayer (Dex Horthy), not Humanloop.** The initial request's "HumanLoop" is a misattribution; Humanloop is an unrelated LLM eval platform. RPI comes from HumanLayer's "Advanced Context Engineering for Coding Agents" (YC talk, 20 Aug 2025) and the repo <https://github.com/humanlayer/advanced-context-engineering-for-coding-agents>, with the working prompts in <https://github.com/humanlayer/humanlayer/tree/main/.claude/commands>. Same lineage as 12-factor agents.

**2. RPI is a means, not the end — the end is context management.** The essay's own framing is "frequent intentional compaction": design the *entire* workflow around keeping context utilisation in the **40–60%** range, because "the contents of your context window are the ONLY lever you have to affect the quality of your output". Optimise for correctness > completeness > size > trajectory; the worst failures in order are incorrect information, missing information, too much noise. Every artifact in the workflow exists to compact something (file searching, code-flow understanding, test/build logs, tool JSON) into a structured document. This reframes our proposal docs: they are compaction boundaries first and approval gates second.

**3. The gate placement is justified by review leverage, not process taste.** "A bad line of a **plan** could lead to hundreds of bad lines of code. And a bad line of **research**… could land you with thousands of bad lines of code." That is the argument for gating hardest at research and design, exactly where the initial request already puts `proposed-research.md` and the ADR walkthrough.

**4. Subagents are context control, not role-play.** "Subagents are not about playing house and anthropomorphizing roles. Subagents are about context control." HumanLayer's research command spawns *named* read-only documentarian subagents — `codebase-locator` (where things are), `codebase-analyzer` (how they work), `codebase-pattern-finder` (existing examples), `thoughts-locator`/`thoughts-analyzer` (prior docs), `web-search-researcher` (external, must return links) — with strict ordering (locators first, analyzers on the promising hits), a hard "wait for ALL subagents before synthesising" rule, and "keep the main agent focused on synthesis, not deep file reading". A generic `Task()`-with-`general-agent` variant is noted as working "almost as well", which is the cheaper starting point for us.

**5. Their research prompt bans opinions outright.** "YOUR ONLY JOB IS TO DOCUMENT AND EXPLAIN THE CODEBASE AS IT EXISTS TODAY… DO NOT suggest improvements… DO NOT perform root cause analysis… DO NOT critique." Our `research-findings-<n>` docs currently do the opposite (they recommend), which is fine — but only if the *ref* docs stay factual. Splitting fact-capture from recommendation is a design decision to make explicitly, and their split is `research` (facts) vs `design-discussion` (opinions).

**6. Their plan prompt is already most of what the initial request asks for.** Interactive and skeptical by construction: read everything mentioned FULLY before spawning subagents; present understanding plus *only* questions research could not answer; if the user corrects you, re-verify rather than accept; present design **options with pros/cons** and ask which; present the **phase outline alone** and get sign-off *before* writing detail. The plan template carries Overview, Current State, Desired End State, Key Discoveries with `file:line`, an explicit **"What We're NOT Doing"** scope fence, per-phase Changes Required, and success criteria split into **Automated Verification** (runnable commands) and **Manual Verification** (UI, load, edge cases), with a per-phase "pause here for manual confirmation from the human before proceeding". Hard rule: **"No Open Questions in Final Plan"** — if one appears, STOP and resolve it. This is directly adoptable prompt text for our plan stage, including the manual-verification instinct the initial request insists on.

**7. Their implement prompt makes the plan file the durable progress ledger.** It reads existing `- [x]` marks, resumes from the first unchecked item, ticks boxes with Edit as it goes, and never ticks a manual-testing item until the user confirms. Mismatches trigger a scripted STOP with Expected / Found / Why this matters / How should I proceed. And notably: "use sub-tasks sparingly" during implementation — fan-out is a research-and-plan tool, not an implementation tool.

**8. HumanLayer have since published what RPI got wrong, and it maps onto risks in our design.** From "Everything We Got Wrong About RPI" (Mar 2026): (a) handing a ticket straight to a research agent made it "generate opinions rather than objective facts"; (b) the planning agent skipped the interactive step ~50% of the time, so users resorted to "magic words" incantations — a prose-only gate is unreliable; (c) frontier models reliably follow only **150–200 instructions**, and an 85-instruction prompt plus system prompt, tools and MCP configs blew that budget, so instructions were followed partially; (d) ~1000-line plans cost as much to review as the code while the code diverged from them anyway; (e) the "don't read AI-generated code" advice was explicitly retracted.

**9. Their answer is more, smaller stages: CRISPY.** Seven stages — Context (research questions), Research, Iterate (design discussion), Structure (outline), Plan, sYnthesize (worktree), Implement — each **under 40 instructions**. The highest-leverage gate is the **design discussion**: a ~200-line markdown of current state, desired state, patterns, resolved decisions and open questions, reviewed by code owners before any plan exists, described as "5x better leverage than reviewing a 1,000-line plan" and where "you catch 80% of the problems". Structure outline (~2 pages, "analogous to C header files") is the second gate. **Our ADR stage is their design discussion.** That is strong independent validation for the ADR stage existing between research and plan — and a warning that our ADRs should be ~200 lines of decisions, not documents.

**10. Their current shipped packaging is one skill per stage, in create/iterate pairs.** <https://docs.humanlayer.com/reference/skills-workflows> lists **22 `rpi:` skills**: `create-research-plan`/`iterate-research-questions`, `create-research`/`iterate-research`, `create-design-discussion`/`iterate-design-discussion`, `create-prd`/`iterate-prd`, `create-tdd`/`iterate-tdd`, `create-outline`/`iterate-outline`, `create-plan`/`iterate-plan`, plus `configure-workspace`, `create-worktree`, `implement-plan`, `implement-outline`, `iterate-implementation`, `describe-pr`, `ci-commit`, `review-artifact-comments`. Artifacts are `NN-<stage>-<slug>.md` in a per-task directory. Four **workflows** (RPI / PRD-oriented / Oneshot / Freeform) select subsets of the same skills by task size — Oneshot goes straight from `ticket.md` to implementation.

**11. Their cross-session handoff is exactly the mechanism spike S2 proposes to validate.** The public `riptide-rpi` entry-point skill's resume path is three lines: "Find task dir; List contents; **Based on which files exist, suggest the next skill to use**." The `NN-` prefix gives order, the filename gives stage, and a stated **artifact precedence — Plan > Structure Outline > TDD > PRD > Design Discussion > Research > Ticket, later wins** — resolves conflicts. Their session guidance is explicit: "before you switch sessions, write every current decision from this session into the artifact", then start a new session with the matching `iterate-*` skill. S2 is therefore low-risk: the pattern is proven in production; what we are validating is our own naming and index conventions, not the concept.

## B. What the platform supports and constrains

**12. Plugin anatomy is settled and cheap.** `.claude-plugin/plugin.json` (the only file in that directory), with `skills/<name>/SKILL.md`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `settings.json`, `bin/` as siblings. Distribution via a repo-level `.claude-plugin/marketplace.json`. Skills in a plugin are addressed as `/<plugin>:<skill>` — so stage skills are individually invocable by construction, which is one of S1's comparison axes and already effectively answered. Docs: <https://code.claude.com/docs/en/plugins.md>.

**13. Progressive disclosure argues structurally for stage skills over one monolith.** Only a skill's `name` + `description` occupy context until it is invoked; once invoked the body stays resident for the rest of the session. A single four-stage `/new-project` skill therefore pays its full token cost from the moment it is invoked through to the end, while four stage skills each pay only during their stage. This is an independent, mechanical restatement of HumanLayer's <40-instructions finding — two different arguments converging on the same shape.

**14. The frontmatter fields we need all exist.** Documented: `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`, and both halves of the invocation axis — **`disable-model-invocation: true`** (user-only) and **`user-invocable: false`** (model-only). Useful substitutions: `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_DATA}` (persists across plugin updates). Caveat: only `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` are valid for claude.ai Agent Skills upload — everything else is a Claude Code extension.

**15. Fan-out has two routes, and the simple one is the right one.** A `context: fork` skill runs in an isolated subagent that inherits project CLAUDE.md, MCP servers and its `allowed-tools`, but **not** the parent's conversation history — so every research subagent prompt must be self-contained, which is precisely why the approved `proposed-research.md` must carry enough per-area detail to seed a subagent brief verbatim. For wider fan-out, dynamic workflows expose `parallel()`/`pipeline()` with documented limits (16 concurrent, 1,000 agents per run, 4,096 items per call). But the proven pattern — HumanLayer's and ours today — is simply instructing the main agent to spawn N Task subagents in parallel and wait for all of them. No scripting, data-driven from the proposal doc.

**16. Plan mode is the only purpose-built approval gate, and it has sharp edges for plugins.** It is a *permission mode*, not a tool allowlist: reads and read-only bash allowed, edits blocked, exiting via `ExitPlanMode` raises the approve/keep-planning prompt. The plan **is** persisted to disk (`plansDirectory`, default `~/.claude/plans`, settable to `./plans`); hooks receive `plan` and `planFilePath`. The constraints that matter: `ExitPlanMode` is stripped from subagents unless the agent frontmatter sets `permissionMode: plan`, and **plugin-shipped agents cannot set `permissionMode` at all**; `EnterPlanMode` is always stripped from subagents, so a `context: fork` skill cannot raise the gate; `ExitPlanMode` blocks in headless `-p`; and in bypassPermissions sessions plan mode is **advisory only**. Conclusion: **never put a stage gate inside a subagent or a forked skill** — gates belong in the main session.

**17. A gate should be layered, not prose-only.** Ranked by reliability: plan mode / `ExitPlanMode` > permission prompts > hooks (`PreToolUse` matching `ExitPlanMode` can deny with a reason to force replanning; `PermissionRequest` can allow/block; `Stop` can intercept turn end; hooks can `setMode` back to `plan` at a stage boundary) > `AskUserQuestion` (a structured-choice primitive — good for "pick option A/B/C" on an ADR decision, unavailable in headless, and its blocking behaviour is contested enough to treat as uncertain) > plain prose "STOP and wait". Prose alone is exactly the ~50% skip rate HumanLayer measured. superpowers resolves this neatly by *wrapping* plan mode: write your own artifact file, then enter plan mode, summarise into the native plan, and call `ExitPlanMode` so the native Approve panel renders the gate.

**18. There is no official convention for a docs-directory stage handoff — it is entirely ours to define.** CLAUDE.md is instructions, auto-memory is Claude's own notes, `--resume` continues the same session, settings.json is config. Files-on-disk is a purely user-side convention with no platform support, tooling or endorsement. Every serious tool invents its own (`thoughts/tasks/<slug>/NN-*.md`, `specs/NNN-slug/`, `openspec/changes/<id>/`, `docs/superpowers/plans/`). This is good news for S2: it costs nothing platform-side, and it is testable by simply opening a fresh session and pointing it at the directory.

**19. Validation tooling exists and one piece of it is unusually well-matched to our testing philosophy.** `claude plugin validate ./plugin` is public (structure/manifest/SKILL.md, `--strict`) and belongs in marketplace CI. `claude plugin eval` is early-access and org-gated, but its grader types — `regex`, `tool_used`, **`tool_order`**, **`file_exists`**, `llm`, `baseline` — test *workflow shape* rather than input-equals-output, which is precisely the kind of test the initial request demands and the kind it forbids. Worth checking enablement before the plan stage sets a verification strategy. `/skill-doctor` is a usage report, not a linter.

## C. Prior art — what to adopt, what to refuse

**20. The single most valuable idea in the prior art is superpowers' scaling law.** "The ceremony scales with the task; the approval gate never does", with the named anti-pattern "'Too Simple To Need Approval' — what scales with simplicity is the artifact, never the approval." Its brainstorming skill is a **three-path router**: *spike* (a feasibility question — answer, no documents, anything built is throwaway), *bounded* (clarifying questions → a short design **in chat** → approval → implement, explicitly "no spec file, no implementation plan document"), *architectural* (the full nine-step treatment). A one-way ratchet upgrades the path mid-task; nothing downgrades. HumanLayer reached the same conclusion independently with their **Oneshot** workflow (ticket.md straight to implementation), and Kiro with its "Quick Spec" bypass. spec-kit's most-cited flaw is that it has no such valve: a six-command minimum producing 7+ artifacts regardless of task size.

**21. The best question discipline comes from spec-kit.** A hard **cap of 3** `NEEDS CLARIFICATION` markers; a `/clarify` pass of **at most 5 questions, exactly one at a time**, each multiple-choice with a "why it matters" line and an explicit `**Recommended:** Option [X]` so the user can answer "yes"; an explicit **don't-ask list** ("make informed guesses… data retention, performance targets, error handling, auth method"); a priority order (scope > security > UX > technical); and the rule "never use a topic label as the question". This is directly transplantable to our ADR walkthrough, which the initial request describes as "go one by one for the decisions required".

**22. spec-kit's other transplantable idea is capability partitioning per stage.** `/analyze` cannot write; `/implement` cannot tick checkboxes (**checkbox marks are reviewer-owned**, which turns a checklist into a real human gate); `/converge` may only append. Enforced through `allowed-tools` this is cheap and makes each stage skill's contract legible. Its `/converge` pass — an append-only reconciliation appending typed gaps (`missing | partial | contradicts | unrequested`) with source refs, and requiring the tasks file to be byte-for-byte unchanged when converged — is a good model for a post-implementation check against the ADRs.

**23. OpenSpec contributes the artifact-lifecycle idea nobody else has, and it maps onto ADRs.** A persistent `specs/<domain>/spec.md` as living truth, with per-change **delta specs** (`## ADDED / MODIFIED / REMOVED Requirements`) that fold into the living spec on archive. ADRs are the natural analogue of that persistent truth: a new effort should be able to emit *delta* decisions against existing ADRs rather than regenerating full documents, with an explicit fold-in step. OpenSpec also contributes the CLI-as-engine / skills-as-steering-wheel split, `validate` as a pre-commit hook, and **escape hatches** (`skip_specs: true`) so the process never forces a fake artifact. Its opposite lesson: with *zero* enforcement, nothing stops an agent skipping straight to code.

**24. Ceremony to refuse, named explicitly.** Mega-templates that are mostly sample content the command is then told to delete (spec-kit's 252-line tasks template); boilerplate blocks pasted into every command prompt (spec-kit's ~400 lines of extension hooks, a sixth of its instruction surface); taxonomies that generate coverage tables nobody reads; unbounded clarifying questions; "constitution"-style files that ship as unfilled placeholders with a "skip gracefully" escape hatch; more than two review loops; plans that inline complete code (you write the implementation twice); state machines most tasks never enter (superpowers' five-round fix loop with model-tier escalation, its O(n²) task-pair conflict scan, its five separate review surfaces); shouty absolutist register borrowed without the evidence behind it; and command-surface creep where four verbs mean "make the artifacts" (OpenSpec's 13 commands, hidden behind a core/expanded profile split).

**25. Handoff to subagents should be by file reference, not by pasted content.** superpowers: "everything you paste into a dispatch prompt… stays resident in your context — hand artifacts over as files"; subagents return under 15 lines and write the rest to disk. Their most expensive observed failure is a controller losing its place and re-dispatching completed work, which they fix with a plan-scoped `progress.md` ledger plus per-task `task-N-brief.md` / `task-N-report.md` in an ephemeral, gitignored workspace. Our `./tmp` convention is the same instinct; the ledger is the missing piece. Related: superpowers deliberately removes human gates *inside* execution ("rulings, not stalls") and instead requires every autonomous decision to be logged as `Ruling: <what> — <why> — <cost if wrong>` and rolled up at the end — a better fit than mid-run check-ins for our "parallelise implementation as much as possible" requirement.

**26. Packaging precedent is mixed, and the outlier is instructive.** spec-kit and OpenSpec ship a CLI that *generates* per-harness skills/commands (40+ and 30+ tools respectively). superpowers ships **pure skills with no slash commands and no `agents/` directory at all**, and solves discovery with a single `SessionStart` hook that injects a ~485-word dispatcher skill into every session, with a `<SUBAGENT-STOP>` guard to stop the mandate recursing into workers. Skills chain by name via `**REQUIRED SUB-SKILL:**` markers, and subagent role prompts are plain sibling markdown files rather than agent definitions. For a single-harness plugin, the superpowers shape is the cheapest thing that works; the SessionStart-injection trick is a heavier alternative to `disable-model-invocation` worth knowing about but probably not worth the always-on context cost for us.

## D. Implications for the plugin's shape

**27. S1 (plugin shape) is close to answered before it is run — reframe it.** Four independent lines of evidence point to **one skill per stage** rather than one routing skill: the 150–200 instruction budget and the <40-per-stage response (finding 8/9); progressive disclosure token economics (13); HumanLayer's own migration from three monolithic command prompts to 22 stage skills (10); and standalone invocability coming free from `/<plugin>:<skill>` namespacing (12). The genuinely open questions S1 should now test are narrower and more useful: (a) does a thin, model-invocable `/new-project` **router** skill on top of user-only stage skills route reliably, or does it just add a hop; (b) do we need **create/iterate pairs** per stage as HumanLayer concluded, or does one skill that detects an existing artifact and revises it work as well at half the surface; (c) does a **task-size router** (spike / bounded / full, per finding 20) actually get taken, or does the model always choose the heavy path.

**28. S2 (stage handoff) should be run, but scoped down.** The mechanism is proven (11, 18); what we are validating is *our* conventions. Test specifically: can a fresh session with no conversation context determine the current stage from the docs directory alone; do our `research-findings-<n>` / `research-ref-<n>-<m>` names carry enough stage information without an `NN-` ordering prefix; do we need an explicit index/status file or is file presence sufficient; and what is our **artifact precedence rule** when an ADR and a plan disagree (HumanLayer's answer: later stage wins, stated explicitly in the docs).

**29. A third candidate spike is now visible — S3, the gate mechanism.** Given finding 16 and 17, the reliability of each gate mechanism in *our* setting is an open empirical question with real design consequences. Compare, on a toy project: prose-only "stop and wait"; `AskUserQuestion`; the superpowers pattern of wrapping native plan mode with `ExitPlanMode`; and a `PreToolUse(ExitPlanMode)` hook enforcing stage preconditions. Measure how often each is actually honoured, and whether each survives a headless `-p` run. This is cheap and it de-risks the single behaviour the whole workflow depends on.

**30. Two adoptions can be made now without a spike, because they are text.** HumanLayer's plan-stage machinery — Automated vs Manual success criteria, the per-phase pause-for-manual-verification block, the "What We're NOT Doing" scope fence, "No Open Questions in Final Plan", and checkbox-in-the-plan-file as the resume ledger — is battle-tested prompt text that satisfies most of the initial request's Stage 3 requirements almost verbatim (see ref 2-1 §2.2–2.3). And spec-kit's question budget with recommended defaults and a don't-ask list (21) is the obvious shape for the ADR walkthrough. Both should land in the ADRs as proposed defaults rather than being re-derived.

**31. One requirement in the baseline is contradicted by the prior art and needs an explicit decision.** The initial request asks for "ideally only 1 ADR". HumanLayer's equivalent artifact — the design discussion — is deliberately ~200 lines, and their stated reason for splitting stages at all is that a single 1,000-line artifact costs as much to review as the code. A single ADR covering research → interfaces → architecture → behaviour for a substantial change will trend toward that size. The reconcilable position is: one ADR *document*, but with a hard length budget and a decisions-only body (options, tradeoffs, recommendation, expected behaviour), with everything factual pushed back into the research refs. This should be an explicit decision in the ADR stage rather than an assumption.
