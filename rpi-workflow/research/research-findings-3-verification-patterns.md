# Research findings 3 — verification patterns

Status: findings, area 3 of [proposed-research.md](./proposed-research.md). Full captured material in [research-ref-3-1-streamlit-verification-companion.md](./research-ref-3-1-streamlit-verification-companion.md) (companion-skill pattern) and [research-ref-3-2-kaos-kind-e2e.md](./research-ref-3-2-kaos-kind-e2e.md) (kind e2e pattern).

## 1. The companion-skill pattern (create/verify) is the right shape for any RPI-produced artifact skill

`create-streamlit-app` and `verify-streamlit-app` ([PR #10](https://github.com/EthicalML/agent-skills-marketplace/pull/10), `plugins/workflow-automations/skills/`) declare their pairing in both directions — the creation skill's SKILL.md says "verify it renders with the `verify-streamlit-app` skill before handing off," the verification skill's frontmatter description ends "Pairs with create-streamlit-app." Neither skill assumes the other ran; the handoff is an explicit named pointer a reader or an agent can follow. The RPI plan stage should require this same pairing wherever a plan PR creates a runnable artifact (an app, a service, a CLI): the plan names the companion verification approach explicitly rather than leaving "how do we know this works" implicit in a generic test-writing instruction.

## 2. Three-tier verification, manual-first, is a directly reusable structure — not a Streamlit-specific idea

`verify-streamlit-app` defines tier 1 (manual loop: screenshot, read, iterate — no files, default during active development), tier 2 (smoke check: one boot-and-render pass, `verify.py`, repeatable gate), and tier 3 (opt-in e2e with real assertions, built "only when the user asks for lasting tests"). This is a general escalation ladder for verification effort against any runnable artifact, and it maps onto the ADR baseline's instructions almost verbatim: "leverage manual verification, run scripts iteratively... never just build a Playwright harness straight away" is tier 1; "verification must stay effective and agile" is tier 2; "end-to-end verification is king" for anything that warrants it is tier 3. The plan stage should encode this ladder generically (not just for browser-driven UIs) and instruct: default to a manual, iteratively-run script under a gitignored `./tmp`; add a scripted smoke gate once the shape stabilises; only build a full e2e/regression harness when the user explicitly asks for lasting tests or the PR is verification-intensive (e.g. a UI component, a multi-service integration).

## 3. Workflow-level test naming and structure, evidenced independently in both sources, is the concrete antidote to "1+1=2" tests

kaos's `operator/tests/e2e/test_agentic_loop_e2e.py` names tests `test_delegation_with_memory_verification`, `test_agent_processes_with_memory_events`, `test_coordinator_has_delegation_capability` — each drives a multi-step real interaction (deploy a CR, wait for readiness, exercise through the gateway, assert an observable side effect) rather than asserting a function's return value against a fixed input. The Streamlit tier-3 example (`assets/tests_e2e_example.py`) leans the same way even at smoke scale: `test_filter_flow` types into a filter and asserts the app survives a rerun cleanly, not that some getter returns some literal. Neither codebase's e2e tests assert input-equals-output. The plan stage should require test names and descriptions to state the workflow being validated (verb phrases describing an interaction and its observable effect), and should flag any proposed test whose assertion reduces to "output field X equals input value Y" as a candidate to cut unless explicitly justified — matching the ADR instruction to avoid such tests "unless there are cases where it EXPLICITLY makes sense."

## 4. Two distinct "real system" verification shapes exist, and the plan stage should pick per-PR rather than force one harness

Streamlit verification stands up one local process and drives a headless browser against it (`create_browser`, `goto`, `collect_errors`, screenshot to a project-local gitignored `tmp/`). kaos's kind e2e stands up a real Kubernetes cluster once (`kind-create` → `kind-load-images` → `kind-e2e-install-kaos`) and runs many pytest files against it, each named per feature area, driving real CRs through a real Gateway (`operator/tests/e2e/conftest.py`: `create_custom_resource`, `wait_for_deployment`, `async_wait_for_healthy`). Both treat "e2e as king" identically in spirit — real system, real interaction, no mocked layer — but differ in cost profile: one process boot vs. one cluster boot. The RPI plan stage should ask, per PR, "what is the smallest real system this PR's verification needs to stand up" and let that answer determine whether the companion is a Playwright-against-localhost harness, a kind-against-a-real-cluster harness, or something else entirely (a real database, a real queue) — never defaulting to a generic mocked unit-test suite as the primary verification claim.

## 5. Parallelisation is bounded by an observed failure mode, not "as many workers as possible" — and the plan stage should require plans to state their own threshold and cap

kaos's `e2e-test` target sizes `pytest-xdist` workers to CPU count but hard-caps at 4, with the reason inline in the Makefile comment: "to avoid 'out of pty devices' errors on high-CPU machines." It also groups with `--dist loadscope` so tests sharing expensive cluster-level fixtures land on the same worker rather than racing across workers, and it keeps a sequential fallback target specifically because parallel failure output is hard to read. This operationalises the ADR instruction to "parallelise when things take more than X" concretely: pick a real time threshold, parallelise past it, but cap workers against a real constraint (resource exhaustion, shared-state races) rather than maximising blindly, and always keep a sequential/verbose escape hatch for debugging a failure. The plan stage should require each PR's verification section to name its own threshold and cap, sourced from the same reasoning (what shared state or resource would break under unbounded parallelism), rather than inherit a boilerplate "-n auto."

## 6. Cheatsheets: no direct precedent found in either source — propose the shape rather than port one

Neither the Streamlit skills nor the kaos kind e2e Makefiles contain a "cheatsheet" artifact in the ADR's sense (a short, user-facing "how do I run/use this" reference introduced at ADR time and kept current through the plan). The closest analogues are the `make help` target in `operator/Makefile` (self-documenting target list) and the numbered `## Workflow` steps in each SKILL.md — both are agent/developer-facing usage summaries, not user-facing review aids. Concrete proposal for the RPI plan stage (detailed in finding 7): the ADR stage introduces a cheatsheet stub per user-facing surface the ADR defines (a skill, a CLI, an API), listing expected invocations and their expected observable result; the plan stage is required to update that stub as each PR lands, and the plan's verification section for a PR is not complete until the cheatsheet reflects what that PR actually shipped. This makes the cheatsheet a living, plan-tracked artifact rather than a one-off ADR appendix, closing the gap neither source codebase currently fills.

## 7. Concrete proposal — how the RPI plan stage should encode verification

Combining findings 1–6, the plan-stage skill (or the shared verification section template it emits per PR) should require, for every PR that produces a runnable or user-facing artifact:

1. **Companion declaration.** Name the verification approach for this PR's artifact explicitly (mirrors finding 1) — e.g. "PR 3 ships the export CLI; verification companion: a manual `./tmp/verify.sh` script exercising the three export modes, escalating to a pytest smoke gate once the CLI's flags stabilise."
2. **Tier selection with an explicit default to tier 1.** State which of manual-loop / smoke-gate / opt-in-e2e applies, and do not schedule a Playwright/pytest harness build as day-one work unless the PR is explicitly verification-heavy (finding 2).
3. **Workflow-shaped test list, named as verb phrases.** Each planned test states the interaction and its observable effect, not "assert output equals input" (finding 3). Any test that reduces to input/output equality must carry an explicit one-line justification or be cut.
4. **Real-system choice named per PR.** State the smallest real system needed (local process + browser, a real cluster, a real DB) and do not default to mocks as the primary verification (finding 4).
5. **Parallelisation clause with a stated threshold and cap.** If verification exceeds a stated wall-clock threshold, state the parallelisation approach and its cap plus the reason for the cap (finding 5), and keep/require a sequential debug path.
6. **Cheatsheet update obligation.** Every PR that changes user-facing behaviour must update the living cheatsheet stub introduced at ADR time before the PR is considered plan-complete (finding 6).

This keeps the plan stage from re-deriving verification philosophy per PR from scratch: it is a fixed six-point checklist, populated with PR-specific answers, directly traceable to the two source patterns captured here and to the ADR baseline's verification section in [000-initial-request.md](../adrs/000-initial-request.md).
